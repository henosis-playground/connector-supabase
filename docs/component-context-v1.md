# Supabase derived component context v1

Authors SHOULD NOT hand-write this JSON. The native-first contract in
[native-authoring-v1.md](native-authoring-v1.md) deterministically derives it from
`supabase/config.toml`, `supabase/migrations/*.sql`, and the minimal `henosis.toml` marker. This
document remains the strict backend wire-format contract for collectors and other integrations.

`henosis.v1.ComponentSpec.connector_context` is opaque to core. For specs assigned to connector
`supabase`, the bytes MUST be UTF-8 JSON matching this document. Unknown versions, unknown fields,
and missing fields fail closed.

```json
{
  "apiVersion": "henosis.dev/supabase-component-context/v1",
  "resourceId": "catalog",
  "target": {
    "stack": "local",
    "project": "henosis-local",
    "database": "postgres",
    "schema": "catalog"
  },
  "migrations": [
    {
      "id": "202607130001_create_items",
      "checksum": "sha256:a3341f85a6bb5a560a50a183a7f98e2433446615acc1448cd2b0e50b2e37eef0",
      "sql": "create table items (id bigint generated by default as identity primary key, name text not null);"
    }
  ],
  "api": {
    "expose": true,
    "anonAccess": "read"
  }
}
```

## Required derived input

- `apiVersion` is exactly `henosis.dev/supabase-component-context/v1`.
- `resourceId` is a stable logical identity matching `[a-z][a-z0-9_-]{0,62}`. It survives spec
  revisions and is the local side of the connector's identity binding. Changing it is a new
  resource, not a rename.
- `target.stack`, `target.project`, and `target.database` select configured connector targets. V1
  accepts only `local`, `henosis-local`, and `postgres` respectively.
- `target.schema` matches `[a-z][a-z0-9_]{0,62}` and cannot be a Supabase, PostgreSQL, or connector
  system schema. V1 binds one resource to one owned schema.
- `migrations` is ordered by strictly increasing `id`. IDs match `[a-z0-9][a-z0-9_-]{0,95}`.
  `checksum` is SHA-256 over the exact UTF-8 bytes in `sql`. A migration ID is immutable: changing
  its checksum after a receipt exists is a plan failure.
- `api.expose` selects whether the schema is included in PostgREST's exposed-schema configuration.
  `api.anonAccess` is `none` or `read`. `read` grants schema usage and SELECT on existing tables to
  the `anon` role; future tables are reconciled on the next pass. Native derivation obtains these
  values from `[api].schemas` and the matching migration `GRANT` statements; they are not duplicated
  in `henosis.toml`.

Migration SQL is non-secret desired input. It MUST NOT contain passwords, tokens, keys, connection
strings, or other secret material. V1 applies each migration transactionally with its schema first
on `search_path`; authors should still qualify cross-schema references explicitly.

V1 is deliberately additive for ordered transitions. A conservative scanner rejects migration SQL
containing destructive/data-rewriting verbs such as `DROP`, `TRUNCATE`, `DELETE`, `UPDATE`,
`ALTER`, `REVOKE`, `COPY`, `CALL`, `DO`, or `CREATE OR REPLACE`. Those operations need an approval
surface before this connector may support them. Removing API exposure is supported because it is a
reconcilable, reversible configuration change and does not delete database objects.

## Slice-wide rules

Every component in a slice MUST select the same stack, project, and database. Resource IDs and
schemas are independently unique. The local v1 target has one exclusive graph owner; a second graph
receives `supabase.plan.target-owned` rather than sharing mutable project configuration implicitly.

Self-hosted Supabase models one project and does not provide the hosted platform's project
management API. Accordingly, v1 does not pretend to create projects or databases. It reconciles the
high-value native seam that exists locally: owned schemas, ordered migrations, grants, and
PostgREST exposure inside one pre-provisioned project.

## Outputs

After re-observation proves every migration receipt, schema, grant, and API setting, each component
publishes this fully known shape:

```json
{
  "project": "henosis-local",
  "database": "postgres",
  "schema": "catalog",
  "apiUrl": "http://127.0.0.1:4484",
  "restUrl": "http://127.0.0.1:4484/rest/v1",
  "databaseUrlRef": "docker-secret://supabase-connection-url",
  "anonKeyRef": "docker-secret://supabase-anon-key"
}
```

The public HTTP URLs contain no credentials. Database URLs and anonymous keys are references to the
trusted target boundary, never plaintext world data. Core therefore never receives a password,
JWT, publishable key, or secret connection string.
